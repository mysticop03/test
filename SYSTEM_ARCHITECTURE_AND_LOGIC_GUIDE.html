💡 1. The Mental Model: What is this App Doing?

Imagine you are an IT/POS operations engineer responsible for hundreds of retail stores. Every store has:

  • 1 Back Office (BO) Server: The central brain inside the store (usually running Ubuntu Linux at IP ending in .12 or .15).
  • Multiple POS Counters / Tills: The cash counters where cashiers bill items (running Ubuntu Linux starting from IP offset .112 up to .211).

Before this tool existed, verifying whether a software update reached every till required manually opening PuTTY / SSH terminal sessions into each cash counter one by one, typing commands, checking file sizes, and inspecting properties files. Doing this across 100 tills in a hypermarket takes hours.

The Solution in One Sentence
This application is an automated multi-threaded SSH auditor and command orchestrator. You give it an IP subnet or an Excel file of stores, choose what to check (files, versions, URLs, or custom Linux commands), and it connects to up to 100 tills simultaneously across 10 parallel stores, runs probes in fractions of a second, and renders real-time color-coded results in an anti-lag table.

🔢 4. How the "100 Tills" & IP Offset Math Works

In retail POS environments, machines are not assigned random DHCP addresses. They follow a predictable IP schema:

Back Office Server (BO) Base Offset

Always fixed at .12 (or .15 depending on store profile):

Subnet: 10.14.22.x
BO IP = 10.14.22.12

POS Cash Counters (Tills) Formula

Starts at .112 and increments by Till number:

Till N IP = Prefix + (112 + (N - 1))
Till 01 = 10.14.22.112
Till 02 = 10.14.22.113
Till 100 = 10.14.22.211

Why 100 is the hard ceiling: In an IPv4 class C subnet (/24), valid host addresses run from .1 to .254. Because tills start at .112, 100 tills reach .211. If a user entered 150 tills, the calculated IP would exceed .255, which is an invalid IP address and would cause network exceptions.

How the UI enforces this in real time:

def _validate_tills_input(proposed):
    if proposed == "":
        return True          # Allow backspacing/empty
    if proposed.isdigit():
        val = int(proposed)
        return 1 <= val <= 100  # Strictly reject 101, 200, -1, etc.
    return False             # Reject letters, symbols, decimals
⚡ 5. Batch Size (Max 10) & Global SSH Budget (100)

When scanning hundreds of stores from an Excel sheet, you cannot launch 5,000 threads simultaneously—your Windows laptop would run out of file descriptors, crash the network card, or trigger firewall flood protection.

The system uses a Sliding Window Concurrency Engine in core/parallel_runner.py:

  1. Store Admission: Stores enter a pending queue. The orchestrator admits up to store_concurrency (Max 10) stores at any given instant.
  2. Connection Budget Check: Before admitting a new store, it checks: 
    if self.active_connections + needed_tills <= self.max_total_ssh_connections:
    # Admit store into active execution window
    The total simultaneous SSH connections across all active stores is hard-capped at 100.
  3. Worker Handover: When all tills of a store finish, the store is retired, its connection budget is refunded, and the next store in the queue slides into the window immediately.
🛡️ 6. How the Safety Guard Blocks rm -rf

In this Unrestricted Edition, operators need to run unrestricted maintenance commands (e.g. systemctl restart, uptime, free -m, sed configuration updates).

However, accidental destructive deletion could wipe an entire POS till during live store hours. The SafetyGuard.is_rm_rf_blocked(cmd) method performs two levels of regex inspection:

1. Combined Flags

Catches bundled arguments where r and f are together:

rm -rf /path
rm -fr /path
rm -rfi /path
\brm\s+-[a-z0-9]*r[a-z0-9]*f

2. Dispersed & Long Flags

Catches arguments separated by spaces or long options:

rm -r -f /path
rm -f -r /path
rm --recursive --force /path
has_r and has_f
Result If Detected
If any rm -rf pattern is matched, execution is blocked on your local machine before any packet is sent to the network, and the console displays:
Security Policy Violation: 'rm -rf' is strictly prohibited across all machines.

⚙️ 8. UI Anti-Freeze & Deterministic Ordering

Why the Tkinter UI Never Freezes

In standard Python Tkinter scripts, running network operations freezes the window, making the OS say "(Not Responding)". Here, all SSH connections run in a dedicated background daemon thread (self._worker_thread). Results are posted into a thread-safe FIFO queue (self.event_queue). The main UI thread runs a lightweight root.after(50, self._consume_events) loop that drains the queue at 20 FPS without ever blocking the UI.

Deterministic Store & Till Ordering

Because network responses arrive asynchronously (Till 5 might respond in 200ms while Till 1 takes 600ms), results arrive out of order. To keep reports human-readable, every target carries: 

store_order_index: int   # Order store was entered by user (1st, 2nd, 3rd)
till_num: int            # Numerical till sequence: BO (0), Till 1, Till 2, ... Till N

The table sorts by (store_order_index, till_num), guaranteeing that outputs always display:
Store 1 → BO → Till 1 → Till 2 → Till 3 ... → Store 2 → BO ...

Thread Safety & The RLock Fix

The RLock Architecture
core/config_manager.py uses threading.RLock() (Reentrant Lock). This allows the main thread to call reload() (which acquires the lock) and then nested internal methods like _load() or get() without deadlocking itself.
